## COLD OPEN (0:00–1:10)

**[SHOW: a CLAUDE.md / AGENTS.md file on screen, scrolling]**

This file is supposed to make my coding agent smarter. Almost everyone building with agents has one — a memory file, hand-written notes the model reads before it works.

In early 2026, researchers at ETH actually measured what these files do. **[SHOW: arXiv:2602.11988 abstract]** Across real repos: no measurable improvement in task success — and about twenty percent higher cost, because the agent reads the file on every single call. And when the file was *generated by the model itself*, it was net negative. The agent's own notes made it worse.

**[BEAT]**

So the most common form of AI memory, the one you probably use, measurably doesn't work. And yet — memory is the thing everyone agrees agents need. Billions of dollars, dozens of startups, every frontier lab.

The problem isn't that memory is fake. It's that "memory" is one word for at least six different things, and almost nobody building with LLMs has the map. By the end of this video you'll have the whole map — every major approach, how each one actually works, how you'd build it yourself this week, and where the frontier actually is as of July 2026. Which, spoiler, is a much more optimistic story than that ETH result suggests.

## PART 1 — WHY MODELS NEED MEMORY AT ALL (1:10–3:00)

Start from zero. A language model is a function. Prompt in, response out. **[SHOW: simple diagram, f(prompt) → answer]** When the call ends, nothing persists. Every conversation starts from the same frozen weights. It's not that the model forgets you — it never knew you. There is no "it" that persists between calls.

Everything the model knows lives in exactly two places, and this is the single most important fact in this video:

**One: the weights.** Billions of parameters, baked in during training. Everything about the world up to its cutoff date. Vast, but frozen, and expensive to change.

**Two: the context.** The tokens you feed it right now. Fresh and fully under your control — but it evaporates when the call ends, and you pay for every token, every call.

**[SHOW: two boxes — WEIGHTS (frozen, huge) / CONTEXT (fresh, rented)]**

So "memory" for an LLM is exactly one problem: **things happen — conversations, projects, months of work — and you want them to still matter later.** Every memory system ever built is some answer to two questions: *where do you put what happened*, and *when do you do the work of organizing it*. Those two questions give us a map.

**Human parallel** (and I'll keep these scientific, because the analogy is real): your brain has the same split. Slow-changing structure built over years — that's the weights. And whatever's in your working attention right now — that's the context. The reason you're not a goldfish is that you have machinery *between* those two: the hippocampus catching today's events, and consolidation — largely during sleep — moving what matters into cortex. LLMs shipped without that middle machinery. This whole field is people trying to bolt it on.

## PART 2 — THE MAP (3:00–4:30)

**[SHOW: the grid map, full view. Hover nothing yet.]**

Here's the map. Down the side: **where knowledge lives.** Three tiers — as re-readable *text*, as pre-computed model state called the *KV cache*, or trained into the *weights*. Across the top: **when you pay to organize it** — at write time when information arrives, at read time when a question arrives, or both.

Two things before we walk it.

First — the top axis, write versus read, is about **economics, not intelligence.** It doesn't set the ceiling on how smart your memory is; it sets your cost curve. Organize at write time and you pay once, then every future question is cheap — that's amortization. Organize at read time and every question is expensive but nothing is ever thrown away. The *side* axis — where knowledge lives — is what sets the ceiling. Keep those straight and half the confusion in this field disappears.

Second — the colors. Teal works on any closed API. Rose needs the model's internals — self-hosting. Amber needs open weights you can train. **[SHOW: hover the legend]** Notice the token row is packed and the other two are sparse. That's not because tokens are the best idea. It's because tokens are the only tier you can build on top of GPT or Claude's API. The map is shaped by access, not merit. Hold that thought, because that gate is falling — that's the optimistic part at the end.

Now let's walk every node. Same questions each time: what's the core idea, how does it actually work, how would *you* run it, and what's the honest catch.

## PART 3 — THE TOKEN TIER (4:30–11:00)

### 3.1 Vector RAG — retrieval (4:30–5:30)

**[SHOW: hover RAG node · then arXiv:2005.11401]**

The foundation of the whole tier: **retrieval-augmented generation**, Lewis and colleagues, 2020. Core idea: don't make the model remember — make it *look things up*.

How it works: split your documents into chunks, run each chunk through an embedding model that turns meaning into a vector — a point in space where similar meanings land near each other. Store the vectors. When a question comes in, embed the question too, grab the nearest chunks, and paste them into the prompt.

Run it yourself: this is genuinely twenty lines. `pip install chromadb openai`, embed, top-k, done. Nearly every memory product on the market — Mem0, Supermemory, most of the rest — is a descendant of this loop with better plumbing.

The parallel: this is **cued recall**. A smell pulls up a childhood memory — the cue lands near a stored trace and drags it into attention. And it has the same failure mode your cued recall does: the *nearest* memory isn't always the *relevant* one. Similarity is not relevance. RAG hands you passages, not understanding — which is the crack the whole rest of this video grows out of.

### 3.2 Reflection / consolidation (5:30–6:30)

**[SHOW: hover REFLECT · then arXiv:2304.03442, the Smallville figure]**

Generative Agents — Stanford, 2023. The famous paper with the little simulated town. Its durable contribution is the **memory stream with reflection**: log every observation raw, then periodically step back and ask the model, "what higher-level things do these observations imply?" — and store *those*, the reflections, for retrieval later.

Core idea: **don't store what happened; store what what-happened means.** Compression at write time.

Run it yourself: no framework. Append-only log, plus a nightly job that asks "what few durable facts did today produce?" and appends the answers to a notes file. Retrieve from notes first, raw log second.

This is the closest analogy to real **memory consolidation** in the whole map. Your hippocampus doesn't archive the day verbatim; during sleep it replays, and the cortex keeps the gist and the meaning, not the transcript. The catch is the part biology solved and we haven't: your consolidation is *tuned by whether it helps you later*. The reflection prompt in these systems is hand-written and never corrected by outcomes. Remember that gap — learned versus hand-coded consolidation — it's where this video ends.

### 3.3 Knowledge graphs, and time (6:30–7:30)

**[SHOW: hover GRAPH · GraphRAG paper, then Zep arXiv:2501.13956]**

Core idea: text is unstructured; **extract entities and relationships** into a graph and answer by walking it. Microsoft's GraphRAG for corpora; Zep's Graphiti made it **bi-temporal** — every edge carries when it was true *and* when the system learned it. "Alice's manager was Bob until March, then Carol" stops being two contradictory sentences and becomes one fact that changed.

That matters more than it sounds, because time is the weakest spot in the entire field — on tests of "what was true as of an earlier date," production memory systems score in the single digits. If your facts change, this is the failure mode to test first.

Run it yourself: a weekend. `pip install graphiti-core`, Neo4j in docker, ingest a week of your agent's logs, then ask it "what changed this week?" — the demo that sells the idea.

Parallel: **semantic memory.** You know Paris is the capital of France without remembering the day you learned it. Graphs are that move — facts lifted out of episodes. The catch: extraction is lossy and LLM-expensive. Whatever the extractor didn't think to keep is gone forever, and you pay that tax on every write.

### 3.4 MemGPT — the agent manages its own memory (7:30–8:30)

**[SHOW: hover MemGPT · arXiv:2310.08560, figure 1 — the OS diagram]**

2023, Packer and colleagues, and the idea that runs half the products in 2026: treat the context window like **RAM**, and give the model an operating system's toolkit. Small always-in-context core memory, big external archive, and — the key move — *tools to page things in and out and rewrite its own notes.* The model is its own memory manager.

Watch the category shift: everything so far *stored knowledge*. MemGPT is a **process** — a behavior. That distinction, storage versus process, is the second axis people conflate, and we'll hit it hardest in the weights tier.

Run it yourself: `pip install letta` — MemGPT's successor — or hand-roll it in an afternoon: give your agent a memory-edit tool and an archival-search tool and a rule for when to use them. This same pattern is now built into the frontier products themselves — Claude's memory tool, ChatGPT's memory. When your ChatGPT quietly writes "user prefers concise answers," that's MemGPT's move.

Parallel: **working memory management** — Miller's famous seven-plus-or-minus-two. You can't hold everything in attention, so you choose what stays. Catch: it's only as good as the agent's own judgment about what's worth keeping. Which, as the ETH result showed, is exactly where self-generated notes go wrong.

### 3.5 Quick pass: notes, wikis, and re-reading everything (8:30–10:15)

Three more token-tier patterns, faster, because you now have the vocabulary:

**Atomic notes** — **[SHOW: hover NOTES · A-Mem, arXiv:2502.12110]** — the Zettelkasten, mechanized: each memory is a small note, automatically *linked* to related notes, and — the good part — old notes get *updated* when new ones arrive. Links give you multi-hop recall a flat pile can't. Runnable today as an MCP server: basic-memory.

**The agent wiki** — **[SHOW: hover WIKI]** — the informal one everyone actually uses: CLAUDE.md, AGENTS.md, Devin's DeepWiki. Plain files the agent reads and edits. Portable, reviewable, git-diffable. This is where that ETH study lives, so say the honest version: a *maintained* wiki is the best effort-to-value memory there is; an *unmaintained* one is a tax. The file isn't the memory — the **habit of consolidating into it** is the memory. Biology agrees: it's not the notebook, it's the nightly review.

**Recursive reconstruction** — **[SHOW: hover RLM · arXiv:2512.24601]** — the purest read-time answer: store *nothing*, keep the raw log, and at question time the model writes little programs to slice and re-read exactly the parts it needs, recursing on each slice. Nothing is ever lost, because nothing was ever summarized. It's episodic re-experiencing — mentally re-walking your morning to find your keys. Costs compute per question, which is precisely the amortization trade from Part 2. Runnable tonight as `dspy.RLM`. Agentic RAG — retrieval in a judged loop — is the same read-time philosophy applied to search.

**[BEAT — SHOW: full token row]**

That's the crowded row. Notice every one of these is ultimately *text the model re-reads*. The model itself never changed. Which is why the interesting question is: what's below this row?

### 3.6 Interlude — the turn (10:15–11:00)

**[SHOW: Machine Studying blog]**

Before we go down a tier, the result that reframes everything. A 2026 study called *Machine Studying* asked: does giving a model search over documents make it an *expert* in them? Two equally capable models, search over the same documents, same passages retrieved — the one that already understood the domain kept the right passages; the other threw them away. **Perfect retrieval, wrong judgment.** And fine-tuning on the raw corpus didn't fix it — that improved *recitation*, not competence. What worked was a **studied artifact**: a compact, worked-through understanding the model built by actively processing the material *before* questions arrived.

Every student watching knows this: re-reading the textbook the night before does nothing. Working the problem sets is what builds the thing exams actually test. **Recall and competence are different products.** The token tier above is a recall machine. The two tiers below are where competence lives.

## PART 4 — THE CACHE TIER (11:00–13:30)

### 4.1 What a KV cache is, in one minute (11:00–12:00)

**[SHOW: transformer diagram, minimal]**

To understand this tier you need one piece of mechanics. When a transformer reads your prompt, it doesn't just skim it — it computes, for every token, at every layer, a pair of internal vectors: keys and values. That's the **KV cache**: the model's *digested* representation of the text, the actual state its attention looks at when generating. Reading a 100k-token corpus means computing all of that, every single call. Notice: that's the same work, producing the same result, thousands of times.

So the obvious move: **compute it once and keep it.** Prompt caching — every provider ships it, vLLM does it automatically — keep your corpus as a byte-identical prompt prefix and cached input bills at roughly a tenth the price. Minutes to set up. If you take one immediately-actionable thing from this video, it's that.

But plain caching is just a receipt for work you already did. The interesting question: could the cache hold something *better* than what re-reading produces?

### 4.2 Cartridges — the star of the map (12:00–13:30)

**[SHOW: hover CARTRIDGE ★ · arXiv:2506.06266, figure 1]**

Stanford's Hazy Research lab, 2025. **Cartridges.** Core idea: instead of *computing* the KV cache from your corpus, **train** a small one — treat the cache itself as trainable parameters.

How it works, and this connects everything we've seen: the recipe is literally called **self-study**. The model generates synthetic conversations about your corpus — quizzes itself, summarizes, connects, rephrases — and a small KV cache is trained by context-distillation until *that little cache*, loaded in front of the model, reproduces what the model would do with the full corpus in context.

The numbers are why this node gets the star: in-context-learning quality at about **38× less memory** and **26× higher throughput**, effective context extended from 128k to nearly half a million tokens — and trained cartridges *compose*: load two, the model can use both, without retraining.

Look at what this is: **Machine Studying's studied artifact, made literal.** Not a summary in text — a digested representation in the model's native format. The parallel is exact: the difference between a student's KV cache computed by skimming and a cartridge trained by self-study *is* the difference between re-reading and doing problem sets. Same material, different processing, different capability.

Run it yourself: the code is open — github.com/HazyResearch/cartridges. A serious weekend: open-weight model, one rented GPU, point self-study at one corpus you query constantly. The catch: it needs internals access — but that's the gate that's falling. This is the most underbuilt high-value spot on the whole map.

## PART 5 — THE WEIGHTS TIER (13:30–17:00)

### 5.1 Getting the conflation out of the way (13:30–14:30)

**[SHOW: the weights row, all three nodes]**

The bottom tier is where people get sloppiest, including researchers, so let's be precise. "Put it in the weights" describes **two completely different things**, and the map badges them separately:

**Storing knowledge in weights** — the facts themselves become parameters. Fine-tuning, distillation. After training, the model *knows* your API without being told.

**Learning a process into weights** — the facts stay in tokens; what's trained is the *skill of managing them*. A learned librarian. The library is still text.

Human version: memorizing the London street map versus *learning how to study*. Both change your brain; they are not the same change. Keep the badge in mind for all three nodes.

### 5.2 Fine-tuning and continued pretraining — stores knowledge (14:30–15:20)

**[SHOW: hover FINE-TUNE]**

The classic: keep training on your corpus until the knowledge is parametric. Zero context cost forever after — the best possible economics. And the classic failure, now with receipts: naive next-token training on a corpus **underperforms just putting it in context**, and it can degrade general ability — the Machine Studying result again, from the weights side. Drilling is memorization, not understanding — cramming, in the exam analogy.

Two facts have changed this story recently, and they're load-bearing. One: the *data* fix — don't train on the raw corpus; train on **studied material about it**: generated Q&A, summaries, worked examples. Self-study again — the same recipe as Cartridges, one tier down. Two: the *operator* fix — reinforcement-style updates instead of supervised ones. In recent head-to-heads, RFT-style training cost about **2% of prior capability where standard SFT cost about 10%** — roughly four times gentler on what the model already knew. That number quietly unlocks *continual* training — updating weights repeatedly without eroding the model. Forgetting was THE reason weights-as-memory was scary. It's becoming an engineering parameter instead of a wall.

Run it: QLoRA on a 4-to-14B open model, Unsloth, one consumer GPU, a weekend.

### 5.3 On-policy distillation — moves knowledge (15:20–16:10)

**[SHOW: hover DISTILL · Thinking Machines blog]**

Subtler and, for practitioners, maybe the most useful idea in the tier: **context distillation**. You have something the model does well *only when its notes are in context*. Distillation moves that ability *into* the weights: the student practices on its own outputs and is graded token-by-token against a teacher that has the notes — until the student no longer needs them.

Thinking Machines showed the on-policy version working cleanly in 2025; it's a recipe in their Tinker product, and TRL's GKD trainer is the open-source route. The catch is honest: you choose what's stable enough to bake in — bake in something that changes next month and you own stale weights.

The parallel is one of the cleanest in the video: **procedural consolidation** — learning to drive. First, everything is explicit instruction held in working memory: mirror, clutch, check blind spot. A year later the skill runs from different brain systems entirely, no narration needed. The instructions got distilled from context into weights. That's this, literally.

### 5.4 RL memory policies — learns a process (16:10–17:00)

**[SHOW: hover RL-MEM · Memory-R1, arXiv:2508.19828]**

And the third node — the badge flips: **Memory-R1** and its successors train the model, by trial and reward, to *decide what to store, update, and delete*, where the reward is whether the eventual answer came out right. The memory bank is still text. What lives in the weights is the **management policy** — the thing every previous system hand-coded in a prompt.

This is the answer to the gap I flagged back in the reflection segment: consolidation *tuned by outcomes*. Biology's version is beautiful and precise: your brain gates what gets consolidated using salience and reward signals — dopamine tags the experiences that mattered, and sleep preferentially replays *those*. Not a hand-written rule. A learned one, trained by consequences.

Honest state of play: this is the youngest node — credit assignment for individual write decisions is genuinely hard and the public results are early. But directionally it's the endgame: it's the only node on the map where the memory system itself *gets better with experience*. Run-it-yourself is real but serious: GRPO via verl or Tinker, reward = downstream answer quality.

## PART 6 — PUTTING IT TOGETHER (17:00–19:30)

### 6.1 The map, re-read (17:00–17:45)

**[SHOW: full map, slow pan]**

Zero to expert, compressed: knowledge lives in three places — text you re-read, caches you pre-compute, weights you train. You organize it at write time or read time — that choice is your **cost curve**, amortization versus flexibility, not your ceiling. Each approach either **stores knowledge or runs a process** — and the deepest current trend is processes going from hand-coded to *learned*. And the crowded row is crowded because of an access gate, not because it won.

One honest confession from our own lab before the sales pitch for optimism. We ran our own memory experiments this year — and the first thing we found was that our *measurement* was broken: the identical memory configuration scored 33, then 67, then 75 percent across reruns of the same eval. **[SHOW: the three numbers]** The variance between runs was bigger than the differences between systems. We caught our harness lying before it caught us — and most published memory benchmarks have exactly this disease, plus worse: the most-cited one has audited errors in its own answer key. So when you build: evaluate on *your* data, with deterministic scoring, multiple runs, before you believe any number — especially your own.

### 6.2 What you should actually do — and why the timing is good (17:45–19:30)

**[SHOW: buyer's guide, the ladder / play-along table]**

If you build with LLMs, this week: **one** — run the sixty-second test: of the questions your agent faces, which could a sharp new hire answer by looking things up, and which need someone who's *worked there*? Lookups: buy recall, it's a mature market, any of the token-tier products serve you well. **two** — before buying anything, price long-context-plus-caching; stable prefix, cache flag, a day of work — a lot of "we need memory" closes right there. **three** — if the second pile matters, the competence pile: the recipe is now public, and this is the optimistic part.

Because here's the actual state of July 2026: everything the frontier labs do behind closed doors is on this map with open code next to it. Background consolidation between sessions? Every serious product does it now, and you can cron it tonight. Studied artifacts? DeepWiki-style tools ship it; the pattern is a prompt away. Self-study caches? Cartridges' code is public. Continual weight updates without catastrophic forgetting? RFT-style training got the forgetting cost down to a few percent. Open-weight models got good enough that the rose and amber gates — the whole reason the map is lopsided — are half-open. Three years ago, "an agent that becomes an expert in *your* domain" was a research program. Today it's a stack: **wiki for structure, RAG for lookup, a cartridge for depth, distillation for what's stable** — a weekend per layer, all of it linked below.

**[BEAT]**

The through-line to leave with: every node on this map is converging on the same missing organ — the thing between the frozen weights and the evaporating context. Biology calls it consolidation: experience, triaged by what mattered, replayed, integrated into structure — on a clock. We're watching that get invented for machines in real time, tier by tier, and for the first time the parts are on GitHub instead of behind a lab door. The people who understand the map get to build with it first.
